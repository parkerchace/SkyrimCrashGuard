[center][size=5][b]What this mod actually does[/b][/size][/center]

The crashes that kill most modded Skyrim sessions are usually access violations. The game reached for something that wasn't there anymore - a dead NPC, a cell reference that expired, an object freed from memory while something else still had a pointer to it. CrashGuard was built specifically for these!

When such a crash occurs, CrashGuard intercepts it before the game can die, reads the exact instruction that failed, and runs it through a six-layer recovery chain. Each layer tries a different approach towards neutralizing the crash. If any of them work, the game keeps running and a log entry records what happened and which mod was involved.

CrashGuard also catches integer divide-by-zero (a mod formula hits a zero denominator) and illegal CPU instructions (code jumps to a garbage address and tries to execute it). These get more limited recovery options, but they're intercepted.

More dangerous types of crashes such as stack overflow, heap corruption, and GPU driver faults, are not prevented. 


Full source code on [url=https://github.com/parkerchace/SkyrimCrashGuard]GitHub[/url] - MIT license.

[b]Who is this for?[/b] Players with large mod lists who keep hitting the same repeatable crash. Mod authors who want to collect multiple crash logs in one session without restarting each time.

[b]Supported versions:[/b] Skyrim SE 1.5.97 / AE 1.6.x (all builds) / VR 1.4.15 - one DLL covers all three.

[b]Requirements:[/b] SKSE64 2.0.x or later (or SKSEVR), Address Library for SKSE, Windows 10/11 64-bit.

[center][size=5][b]How it works[/b][/size][/center]

[b]Why Skyrim crashes in the first place[/b]

Every object in Skyrim - every NPC, item, spell, particle effect - lives at a specific address in your computer's memory. The code tracks where things are through pointers: small notes recording that address. A particle effect attached to an NPC remembers, "the NPC's data is at address 0x12345678", for example.

When the NPC dies and the engine cleans it up, that memory is freed. But the particle effect still has its old pointer. If something tries to read from 0x12345678 after it's been freed, that memory no longer belongs to anything. The CPU can't complete the read and it signals an access violation.

This is why heavily-modded Skyrim crashes so often. More mods means more systems tracking more objects, more chances for one system to read from memory that another already freed.

[b]What Windows does when a crash occurs[/b]

When the CPU signals a fault, Windows doesn't end the process immediately. First it works through a list of registered exception handlers - think of these as software that have told Windows in advance: "call me when something goes wrong." Vectored Exception Handling (VEH) handlers are first on that list, before anything else in the program runs.

Most crash-handling tools - including NVAC (New Vegas Anti-Crash) - use a different approach called Structured Exception Handling (SEH). With SEH, the programmer wraps specific sections of their own code in try/catch blocks. Those blocks only catch crashes that happen inside them. A crash inside a mod DLL the programmer never saw - which is most crashes in heavily-modded Skyrim - is invisible to SEH.

VEH has no such limitation. It's registered with Windows at the process level, not around specific code. Windows calls it for every fault in the entire game - base game, SKSE, any mod DLL, anywhere. CrashGuard doesn't need to know in advance where a crash will come from. When one occurs anywhere in the process, CrashGuard is called first.

[b]What CrashGuard actually does[/b]

When an access violation occurs, Windows saves a snapshot of the processor's state at that exact moment - the register, the address of the crashed instruction, what the CPU was doing. It passes that snapshot to CrashGuard.

CrashGuard's first job is to figure out what instruction crashed and what it was trying to do. An address alone tells you nothing - you need to know whether the instruction was a read, a write, a function call, or something else. CrashGuard reads the raw bytes at that address and feeds them into Zydis, an x86/x64 instruction decoder. Zydis translates those bytes into something meaningful: "the instruction here is MOV RCX, [RAX] - a read that was supposed to load a value from the address held in register RAX and store it in register RCX."

Now CrashGuard knows exactly what to fix. RAX pointed to freed memory. The fix: make the instruction look like it ran successfully but found nothing. CrashGuard edits the snapshot Windows passed it:

[list]
[*]Sets RCX to zero. That's the register that was going to hold the result. Zero means "nothing here" throughout Skyrim's code - the engine uses it as the standard signal for a missing or empty value.[/*]
[*]Advances the game past the crashed instruction. Zydis reported the exact byte length of the instruction, so CrashGuard moves forward by precisely that amount.[/*]
[/list]

Then CrashGuard tells Windows: resume. Windows writes those values back into the actual CPU registers and the game continues. From the game's perspective, it read from the NPC's old address and got zero back - the same thing it gets from any normally missing object.

No patching the game binary. No advance knowledge of where crashes will come from. The instruction at the crash site tells CrashGuard everything it needs.

Crashes CrashGuard doesn't handle - stack overflows, heap corruption, GPU driver faults - pass straight through and proceed to crash the game.

[b]The six-layer recovery chain[/b]

When CrashGuard's VEH handler sees an access violation, it runs it through six layers in sequence. Each layer tries a different approach, starting with the most targeted and working toward the most general. The first layer that can handle the crash does so, and the rest are skipped.

[list=1]
[*][b]L1 - Pre-registered crash locations[/b]

CrashGuard has a built-in list of specific locations in the game's code where crashes are known to happen and where a recovery has been confirmed to work. When a crash arrives, the first thing CrashGuard does is check whether the crash address is in that list. If it is, recovery happens immediately with no further analysis.

If the address isn't in the list, move to L1b.
[/*]
[*][b]L1b - Instruction pattern matching[/b]

CrashGuard reads the exact machine instruction that failed - the specific operation the CPU was executing when things went wrong. It checks whether the instruction matches one of four recognizable crash patterns:

- A call through a null pointer (the object the code was trying to call a function on is gone)
- A jump through a null pointer
- A read from an address that doesn't exist or is no longer valid
- A write to an address that doesn't exist or is no longer valid

CrashGuard reads these instructions using a decoder called Zydis - think of it as a translator between raw CPU instructions and something a program can reason about. If the instruction matches one of the four patterns, CrashGuard knows how to neutralize it: cancel the call, return zero for the read, or drop the write.

This works across all Skyrim versions (SE, AE, VR) because it reads the actual instruction rather than relying on version-specific memory addresses.

If the pattern doesn't match, move to L2.
[/*]
[*][b]L2 - Memory of past recoveries[/b]

If CrashGuard has already handled a crash at this exact memory address earlier in the same session, it remembers the solution. Up to 512 locations can be remembered this way. When the same address crashes again, CrashGuard skips all the analysis and applies the remembered approach immediately.

If this is the first time this address has crashed, move to L3.
[/*]
[*][b]L3 - Redirect the bad address[/b]

If the crash involves reading from or writing to an invalid memory address, CrashGuard redirects that read or write to a small reserved area of empty memory (64KB set aside specifically for this) and lets the instruction complete. The game reads garbage data or writes to a throwaway location, but it doesn't crash.

This is limited to 3 attempts per crash address. If the same location keeps crashing past that limit, L3 stops trying and moves on.
[/*]
[*][b]L4 - Skip the instruction[/b]

CrashGuard skips the crashed instruction entirely, zeroes out whatever register it was supposed to write to, and continues from the next instruction. This is more disruptive than the earlier layers because the skipped instruction never runs - but it keeps the game going. Results are stored in L2 so future crashes at the same address skip straight here.
[/*]
[*][b]L5 - Exit the crashed function[/b]

CrashGuard abandons the function that crashed entirely, jumps back to wherever that function was called from, and returns a null result. The caller gets nothing where it expected something. Riskier than L4.
[/*]
[*][b]L6 - Find a way out[/b]

Last resort. CrashGuard scans up to 8KB of the call stack looking for any valid return address it can jump to. Things aren't looking good here - it's trying to find any exit from the crashed code and resume somewhere that isn't completely broken.
[/*]
[/list]
If all six layers fail, CrashGuard passes the crash to Crash Logger or Trainwreck if either is installed - and the game closes.

The recovery chain has limits designed to prevent it from looping forever on a crash it can't resolve:

- If 100 crashes happen within 5 seconds across the entire session, a global stop kicks in
- Individual crash addresses are limited to 3 L3 redirect attempts
- There's a minimum 5ms gap enforced between recoveries

When any of these limits are hit, CrashGuard stops intervening and the game crashes normally. This is intentional - it means the mod is encountering something it cannot resolve and continuing to try would only make things worse.

[b]Disabling CrashGuard mid-session[/b]

Open the F11 menu and use the Configuration tab to turn CrashGuard on or off. This takes effect immediately - no restart needed.

To verify the mod is actually doing something: open the Diagnostics tab, set the tier to Live, and run any test - CrashGuard will prevent the crashes. Then, disable CrashGuard/VEH under the Configuration tab and run a test again - it should crash and default to CrashLogger or Trainwreck if installed. That should be proof the crash tests/handling are real, but not necessarily that they're safe. [b]You assume all risks when continuing past crashes.[/b]

[center][size=5][b]What types of crashes can be recovered[/b][/size][/center]

[b]These crash types will still CTD - CrashGuard won't help with them:[/b]
[list]
[*][b]Stack overflow[/b] - The game ran a chain of function calls so deep it ran out of room. Usually caused by a Papyrus script that calls itself in a loop or deeply nested mod functions that never exit. There's no way to unwind from this.[/*]
[*][b]Heap corruption[/b] - A mod wrote to memory it didn't own and damaged the game's memory manager itself. Once the memory manager is broken, the game cannot continue reliably.[/*]
[*][b]System DLL crashes[/b] - Crashes inside Windows itself (ntdll.dll, kernel32.dll) or your GPU drivers. These are outside the game process and CrashGuard can't reach them.[/*]
[*][b]Crashes during game exit[/b] - When you close Skyrim, some cleanup crashes are expected and harmless. CrashGuard doesn't intervene during shutdown.[/*]
[*][b]Crashes after recovery limits are exceeded[/b] - If too many crashes happen too fast, the recovery chain stops to prevent runaway loops. The game crashes normally at this point.[/*]
[/list]

[b]These crash types CrashGuard can often handle:[/b]

[list]
[*][b]Null pointer reads.[/b] Something in the game tries to read data from an object that no longer exists - an NPC that was cleaned up, a cell that was unloaded, a reference that expired. CrashGuard intercepts the read and returns zero instead of crashing. This is the single most common crash type in modded Skyrim.
[/*]
[*][b]Null pointer writes.[/b] Same situation, but the game is trying to write data to the missing object instead of reading it. CrashGuard drops the write entirely. The game continues, but the value that was supposed to be updated never gets updated. In practice this usually means a stat doesn't change or an effect doesn't apply - which is far better than a crash to desktop for something like modded Skyrim VR which can take minutes to startup.
[/*]
[*][b]Bad virtual function calls (vtable crashes).[/b] Every NPC, item, weapon, and object in Skyrim has a list of functions it can perform - called a vtable. When the object is removed from memory but something else still tries to call one of those functions, the vtable read finds nothing and crashes. CrashGuard cancels the function call before it can crash. The caller gets nothing back and moves on.
[/*]
[*][b]RaceMenu crashes.[/b] RaceMenu (which uses skee64.dll internally) has several well-documented crash locations in its overlay and body morph system. CrashGuard has pre-registered fixes for these specific locations in the L1 table, so they're handled immediately without analysis.
[/*]
[*][b]Particle system crashes.[/b] Fire, sparks, magic effects - these use a system called NiParticleSystem. When the object a particle effect was attached to gets removed from memory, the particle system can crash trying to read from the missing object. CrashGuard catches these vtable failures.
[/*]
[*][b]Interior cell lighting crash.  [/b]A specific crash in the shadow frustum calculation (SkyrimSE.exe+0x14F400E) where a null shadow frustum pointer causes a read fault. CrashGuard catches this through the recovery chain - because the faulting instruction has no output register to zero, recovery exits the shadow function entirely via a stack walk. 
[/*]
[*][b]Sky and moon texture crashes.[/b] These can happen during save/load cycles when the sky system is briefly in an invalid state. CrashGuard catches the access violation during the transition.
[/*]
[*][b]SIMD floating-point instruction crashes.[/b] Certain math instructions the CPU uses for 3D calculations (movss, movsd, movaps, movups) can crash when they try to read from a null pointer. CrashGuard intercepts these reads and returns zero.
[/*]
[*][b]Integer divide-by-zero.[/b] When mod code divides by zero in an integer calculation - a damage formula, a level ratio, a counter that wasn't initialized. CrashGuard zeroes the result registers and skips past the instruction or exits the function.
[/*]
[*][b]Illegal CPU instruction.[/b] When a corrupted function pointer causes the CPU to jump to garbage data and try to execute it. CrashGuard attempts to exit the crashed function and return to the caller.[/*]
[/list]

[b]SSE Engine Fixes and CrashGuard do different things.[/b] Engine Fixes applies targeted patches to specific known bugs in the engine's code. CrashGuard handles crashes at runtime as they happen. They work well together and running both is better than either alone, in my opinion - IDK, I've just been dealing with Skyrim crashes for 15 years.

[b]ImGui conflicts:[/b] Other mods that use ImGui/other overlay libraries may conflict with the F11 menu. If you see visual glitches or a broken overlay, you can disable CrashGuard's menu. Here's how:

[list=1]
[*]Find the [font=Courier New]SkyrimCrashGuard.toml[/font] file (see Installation above for where it is)[/*]
[*]Right-click it and choose "Open with," then select Notepad[/*]
[*]Look for a line that says [font=Courier New][ImGui][/font] - it has square brackets around it[/*]
[*]A few lines below that, find [font=Courier New]disableMenu = false[/font][/*]
[*]Change [font=Courier New]false[/font] to [font=Courier New]true[/font] so it reads [font=Courier New]disableMenu = true[/font][/*]
[*]Save the file (Ctrl+S) and restart the game[/*]
[/list]

The crash recovery and logging still work normally with the menu disabled.

[b]Crash throttling:[/b] If a mod DLL causes 20 or more crashes within 2 seconds - which some animation mods do during specific transitions - CrashGuard enters silent recovery mode for that DLL. Crashes are still intercepted but per-crash log spam is suppressed. A summary is written every 60 seconds while in silent mode.

[center][size=5][b]FAQ[/b][/size][/center]

[b]Q: I heard this mod "disables crashes" and that sounds dangerous. Is that accurate?[/b]
A: Not quite. CrashGuard only responds to access violations. When CrashGuard sees one, it checks whether it recognizes the pattern. If it does, it handles it. If it doesn't, it steps aside and the game crashes normally. It doesn't try to intercept crashes it doesn't understand, and it doesn't touch crash types it has no way to handle. The recovery limits described above also mean it stops intervening entirely if too many crashes happen in quick succession. I also make no guarantee of safety and will reassert that this is experimental. 

[b]Q: Is the source code available?[/b]
A: Yes. Full source on [url=https://github.com/parkerchace/SkyrimCrashGuard]GitHub[/url], MIT license. The recovery chain, every registered crash location, every layer - all public. This is a FOR FUN project so expect things to be rough around the edges. 

[b]Q: Will this prevent all crashes?[/b]
A: No. The majority of crash types are not in scope for this mod. If you're still crashing frequently after installing CrashGuard, run Crash Logger or Trainwreck alongside it to get detailed reports and identify the actual cause.

[b]Q: Does this replace/break Crash Logger or Trainwreck?[/b]
A: No. CrashGuard handles what it can and writes recovery logs for those crashes. Crash Logger and Trainwreck produce detailed analysis reports for crashes CrashGuard can't handle. Run all three together if you so choose!

[b]Q: Are my saves going to be corrupted?[/b]
A: There's no guarantee. If CrashGuard keeps the game running after a crash, the game state after that point may have problems - the crash happened for a reason, and CrashGuard didn't resolve the underlying cause, it just kept the game from dying at that moment. Saves made right after a recovery may contain issues you won't notice until later. Keep backups. In practice, no one has reported a corrupted save from CrashGuard since v2.2.x, but the risk is real.

[b]Q: Can I turn it off without restarting the game?[/b]
A: Yes. Open F11 and use the Configuration tab to toggle it. Takes effect immediately. To verify it's actually off: open the Diagnostics tab, set the tier to Live, and run any test - with CrashGuard off, the test will crash the game to desktop because the crash is real. Turn CrashGuard/VEH back on and the same test completes successfully.

[b]Q: How does this compare to NVAC?[/b]
A: NVAC (New Vegas Anti-Crash) was a well-regarded mod for Fallout: New Vegas that used Structured Exception Handling (SEH). Here's the difference in plain terms:

With SEH, the programmer places "try/catch" blocks around specific sections of code they expect might crash. Those blocks only work inside the specific code they wrap. If a crash happens somewhere else - in a mod the tool's author never saw, or inside a function they didn't anticipate - the SEH block never runs.

VEH (what CrashGuard uses) works differently. Windows calls it for every crash in the entire game process - in the base game, in SKSE, in any mod DLL, anywhere. CrashGuard doesn't need to know in advance where a crash will come from. If an access violation occurs anywhere, CrashGuard sees it first.

NVAC was built for a specific game targeting specific known crashes. CrashGuard is aimed at the much messier environment of heavily-modded Skyrim, where crashes can come from any of hundreds of mod DLLs interacting in ways nobody planned for.

[center][size=5][b]Configuration[/b][/size][/center]

The config file is at [font=Courier New]Data\SKSE\Plugins\SkyrimCrashGuard.toml[/font]. Open it with Notepad. Each setting has a comment above it explaining what it does.

[b][General][/b] - Turn the whole mod on or off. Set log verbosity (0 = off, 1 = errors and warnings only, 2 = info [b]by default[/b], 3 = debug, 4 = trace (very verbose)).
[b][VEH][/b] - Turn crash recovery on or off. Set the cascade limit. Configure per-module crash throttling.
[b][ProactiveValidation][/b] - Mesh validation and script monitoring. Animation and cell validation settings exist in the file but those systems are not active in this version.
[b][Notifications][/b] / [b][UserNotifications][/b] - Control in-game toasts and popup dialogs.
[b][ImGui][/b] - Disable the F11 overlay, or enable it in VR.
[b][PerformanceOverlay][/b] - Turn on a small HUD showing FPS, memory usage, and crash stats.
